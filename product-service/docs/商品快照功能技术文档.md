# 商品快照功能技术文档

## 1. 功能背景与目标

### 1.1 问题背景

在零食商城系统中，商品信息（价格、名称、图片、库存等）会随运营需求频繁变动。然而，订单系统需要依赖**下单时刻**的商品信息来完成交易、对账和售后。如果订单直接引用当前商品表数据，将面临以下问题：

- **价格不一致**：商品调价后，历史订单的金额与商品展示价格不匹配
- **信息丢失**：商品下架或修改名称后，历史订单无法还原下单时的商品状态
- **审计困难**：无法追溯商品在某一时间点的具体信息，影响财务对账和纠纷处理

### 1.2 设计目标

| 目标 | 说明 |
|------|------|
| 数据不可变性 | 快照一旦创建不可修改，完整保留商品在特定时刻的状态 |
| 透明集成 | 商品更新时自动创建快照，对调用方透明 |
| 可追溯性 | 支持按商品 ID 查询完整的变更历史 |
| 跨服务可用 | 订单服务可通过快照 ID 获取下单时的商品原始信息 |

## 2. 核心业务场景

### 2.1 场景一：商品更新自动存档

```
运营人员修改商品价格（59.90 → 69.90）
        │
        ▼
  ┌─────────────┐     ┌──────────────────┐
  │ updateProduct│────▶│ createSnapshot    │
  │ (ProductService)   │ (SnapshotService) │
  └──────┬──────┘     └────────┬─────────┘
         │                     │
         │  更新前数据写入       │  快照表
         │  t_product_snapshot  │
         ▼                     ▼
  ┌─────────────────────────────────┐
  │  执行商品字段更新                  │
  │  productMapper.updateById()      │
  └─────────────────────────────────┘
```

**时序说明**：在 `ProductServiceImpl.updateProduct()` 中，先查询当前商品数据，调用 `snapshotService.createSnapshot(product)` 将**更新前**的数据写入快照表，再执行实际的字段更新。整个过程在同一个事务内完成。

### 2.2 场景二：订单创建引用快照

当前订单服务（`OrderServiceImpl.createOrder()`）通过 OpenFeign 调用商品服务获取实时商品信息，并将商品名称、图片、价格冗余存储到 `t_order_item` 表。引入快照后，下单流程可改为：

```
订单服务                        商品服务
   │                              │
   │  1. 查询商品详情               │
   │─────────────────────────────▶│
   │                              │
   │  2. 返回商品信息               │
   │◀─────────────────────────────│
   │                              │
   │  3. 创建快照（可选）           │
   │─────────────────────────────▶│
   │                              │
   │  4. 返回快照 ID               │
   │◀─────────────────────────────│
   │                              │
   │  5. 存储快照 ID 到订单明细      │
   │     (order_item.snapshot_id)  │
```

> 注：当前订单服务仍使用 `OrderItem` 冗余字段方案（`productName`、`productImage`、`productPrice`），后续可迭代为引用快照 ID 的方式。

### 2.3 场景三：历史订单回溯

当需要查看某笔历史订单对应的商品信息时，通过 `snapshot_id` 查询快照表，可获取下单时刻的商品完整状态，不受后续商品变更影响。

## 3. 数据模型设计

### 3.1 表结构

```sql
CREATE TABLE `t_product_snapshot` (
    `id`          BIGINT        NOT NULL AUTO_INCREMENT  COMMENT '快照ID',
    `product_id`  BIGINT        NOT NULL                 COMMENT '商品ID',
    `category_id` BIGINT        DEFAULT NULL              COMMENT '分类ID',
    `name`        VARCHAR(200)  NOT NULL                  COMMENT '商品名称',
    `cover_image` VARCHAR(500)  DEFAULT NULL              COMMENT '封面图片URL',
    `price`       DECIMAL(10,2) NOT NULL                  COMMENT '价格',
    `stock`       INT           NOT NULL DEFAULT 0        COMMENT '库存',
    `description` VARCHAR(500)  DEFAULT NULL              COMMENT '简介',
    `detail`      TEXT          DEFAULT NULL              COMMENT '详情',
    `status`      TINYINT       NOT NULL DEFAULT 1        COMMENT '状态：0-下架 1-上架',
    `created_at`  DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    PRIMARY KEY (`id`),
    KEY `idx_product_id` (`product_id`),
    KEY `idx_created_at` (`created_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='商品快照表';
```

### 3.2 与商品主表对比

| 字段 | t_product | t_product_snapshot | 差异说明 |
|------|-----------|-------------------|---------|
| id | 有 | 有 | 快照独立主键 |
| product_id | 无 | **有** | 快照通过此字段关联原商品 |
| deleted | 有（逻辑删除） | **无** | 快照不可删除，无逻辑删除 |
| updated_at | 有 | **无** | 快照不可修改，无更新时间 |
| created_at | 有 | 有 | 快照创建时间即代表快照时间点 |

### 3.3 设计决策

- **冗余存储分类 ID**：快照中保留 `category_id` 而非 `category_name`，分类名称通过实时查询分类表获取。若分类信息也需要快照化，可后续扩展。
- **无逻辑删除**：快照表无 `deleted` 字段，快照数据一旦写入即不可变、不可删除，保证审计完整性。
- **索引策略**：`idx_product_id` 支持按商品 ID 查询变更历史；`idx_created_at` 支持按时间排序和范围查询。

### 3.4 ER 关系图

```
┌─────────────────┐         ┌─────────────────────────┐
│   t_product      │         │   t_product_snapshot     │
├─────────────────┤         ├─────────────────────────┤
│ id (PK)         │◀───┐    │ id (PK)                 │
│ category_id     │    │    │ product_id (FK→product) │
│ name            │    └────│ name                    │
│ price           │         │ price                   │
│ stock           │         │ stock                   │
│ ...             │         │ ...                     │
│ deleted         │         │ created_at              │
│ updated_at      │         │ (无 deleted/updated_at)  │
└─────────────────┘         └─────────────────────────┘
       1                            N
       │                            │
       └──────── product_id ────────┘
```

## 4. 关键技术实现细节

### 4.1 分层架构

```
Controller 层
├── ProductSnapshotController        快照查询 API
│
Service 层
├── ProductSnapshotService           快照业务接口
├── ProductSnapshotServiceImpl       快照业务实现
├── ProductServiceImpl               商品更新时触发快照创建
│
Mapper 层
├── ProductSnapshotMapper            快照数据访问
│
Model 层
├── ProductSnapshot (Entity)         快照实体
├── ProductSnapshotVO                快照视图对象
├── ProductSnapshotQueryDTO          快照查询参数
```

### 4.2 快照创建时机

快照创建嵌入在 `ProductServiceImpl.updateProduct()` 方法中，核心流程：

```java
@Transactional(rollbackFor = Exception.class)
public ProductVO updateProduct(Long id, ProductDTO dto) {
    Product product = productMapper.selectById(id);    // 1. 查询当前商品
    // ... 校验 ...
    snapshotService.createSnapshot(product);            // 2. 创建更新前快照
    // 3. 执行字段更新
    productMapper.updateById(product);
    return convertToVO(product, getCategoryMap());
}
```

**关键设计点**：

- 快照创建和商品更新在**同一事务**中，保证原子性
- 快照记录的是**更新前**的数据状态，而非更新后的
- 使用构造器注入 `ProductSnapshotService`，遵循依赖倒置原则

### 4.3 快照查询

提供两种查询方式：

| API | 路径 | 说明 |
|-----|------|------|
| 单条查询 | `GET /product/snapshot/{id}` | 按快照 ID 精确查询 |
| 分页查询 | `GET /product/snapshot/list` | 支持按 `productId` 过滤，按 `createdAt` 倒序 |

### 4.4 分类信息关联

快照表仅存储 `category_id`，分类名称和排序通过查询分类表获取。为避免 N+1 查询问题，采用**批量预加载**策略：

```java
// 一次查询所有分类，构建 Map
Map<Long, ProductCategory> categoryMap = categoryMapper.selectList(null)
    .stream()
    .collect(Collectors.toMap(ProductCategory::getId, c -> c));

// 遍历时从 Map 取值，无额外 DB 查询
ProductCategory category = categoryMap.get(snapshot.getCategoryId());
```

## 6. 性能优化策略

### 6.1 数据库索引

| 索引 | 字段 | 用途 |
|------|------|------|
| `PRIMARY` | `id` | 主键查询 |
| `idx_product_id` | `product_id` | 按商品 ID 查询变更历史 |
| `idx_created_at` | `created_at` | 按时间排序/范围查询 |

### 6.2 批量分类查询

在 `getSnapshotList()` 中，分类信息通过一次批量查询获取并缓存到 `Map`，避免在循环中逐条查询：

```
优化前（N+1 问题）：               优化后（批量查询）：
  查询快照列表 (1次)                 查询快照列表 (1次)
  遍历每条快照:                     批量查询分类 (1次)
    查询分类 (N次) ❌               遍历快照从 Map 取值 (0次 DB)
```

### 6.3 分页查询

使用 MyBatis-Plus 分页插件，避免全量加载后内存分页：

```java
Page<ProductSnapshot> page = new Page<>(queryDTO.getPageNum(), queryDTO.getPageSize());
Page<ProductSnapshot> result = snapshotMapper.selectPage(page, wrapper);
```

### 6.4 存储增长预估与应对

快照表的数据量 = 商品更新次数。以当前 6 个初始商品为例，数据增长可控。若未来更新频率较高，可考虑：

- 定期归档历史快照到冷存储
- 对超过一定时间的快照进行压缩或清理
- 根据业务需求设定快照保留策略（如仅保留最近 N 条）

## 7. 异常处理机制

### 7.1 统一异常体系

```
BusinessException (自定义业务异常)
       ▲
       │
BusinessExceptionEnum (异常枚举)
  ├── PRODUCT_NOT_FOUND    商品不存在
  ├── STOCK_NOT_ENOUGH     库存不足
  └── ...
```

快照查询时，若快照不存在，抛出 `PRODUCT_NOT_FOUND` 异常，由全局异常处理器统一捕获并返回标准错误响应。

### 7.2 事务一致性

快照创建与商品更新在同一事务中：

```java
@Transactional(rollbackFor = Exception.class)
public ProductVO updateProduct(Long id, ProductDTO dto) {
    // 1. 查询商品 → 若不存在抛异常，事务回滚
    // 2. 创建快照 → 若失败抛异常，事务回滚
    // 3. 更新商品 → 若失败抛异常，事务回滚
    // 任一步骤失败，所有操作全部回滚
}
```

### 7.3 空值防御

在分类信息关联时，对 `categoryId` 和分类查询结果进行空值检查：

```java
if (snapshot.getCategoryId() != null) {
    ProductCategory category = categoryMap.get(snapshot.getCategoryId());
    if (category != null) {
        vo.setCategoryName(category.getName());
        vo.setCategorySort(category.getSort());
    }
}
```

## 8. 方案选型论证

### 8.1 备选方案对比

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| **A. 独立快照表（当前方案）** | 新建 `t_product_snapshot` 表，每次更新前插入快照记录 | 实现简单；查询直观；与现有架构一致 | 数据量随更新次数增长 | **采纳** |
| B. MySQL 历史表 | 使用 MySQL Enterprise 的历史表功能 | 数据库原生支持；透明 | 依赖 MySQL 企业版；灵活性差 | 不采纳 |
| C. Event Sourcing | 记录所有商品变更事件，通过事件回放还原状态 | 完整的变更审计；支持任意时间点还原 | 实现复杂度高；查询性能差；需要 CQRS 架构支撑 | 不采纳 |
| D. 订单表冗余全部商品信息 | 在 `OrderItem` 中存储所有商品字段（当前部分实现） | 查询无需关联；性能好 | 数据冗余度高；存储浪费；字段同步维护成本大 | 部分采纳（当前过渡方案） |
| E. Temporal Table | 使用数据库时态表功能 | 标准化；自动管理版本 | 仅部分数据库支持；查询语法特殊 | 不采纳 |

### 8.2 选择方案 A 的理由

1. **架构一致性**：与项目现有的分层架构（Controller → Service → Mapper）完全一致，无需引入新的架构模式
2. **技术栈匹配**：基于 MyBatis-Plus + MySQL，无需额外中间件或数据库特性
3. **实现成本低**：仅需新增一张表和对应的 CRUD 代码，对现有代码侵入性小
4. **查询性能好**：快照数据直接存储在关系表中，查询无需事件回放或复杂计算
5. **可演进性强**：后续可平滑扩展为支持按时间范围查询、快照对比、版本回滚等功能

### 8.3 方案 A 的已知限制

- **存储增长**：每次商品更新都会产生一条快照记录，长期运行需关注存储容量
