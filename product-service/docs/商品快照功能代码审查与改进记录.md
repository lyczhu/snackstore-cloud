# 商品快照功能代码审查与改进记录

> 适用模块：`product-service`
> 涉及文件：`ProductSnapshotController` / `ProductSnapshotServiceImpl` / `ProductSnapshotQueryDTO` / `ProductSnapshot` / `ProductServiceImpl` / Flyway V3 / `ResultCode` / `BusinessExceptionEnum`

---

## 一、问题清单

| No. | 等级 | 问题 | 影响 |
|-----|------|------|------|
| #1 | Major | 快照触发场景不完整：仅 `updateProduct` 落快照，`createProduct` / `deleteProduct` / `updateProductStatus` 均缺失 | 商品生命周期关键节点无历史轨迹可查 |
| #2 | Major | `getSnapshotById` 找不到快照时抛 `PRODUCT_NOT_FOUND`，错误码语义错误 | 调用方无法区分"商品不存在"与"快照不存在" |
| #3 | Major | 分类信息（`category_name` / `category_sort`）未冗余落库，仅存 `category_id`，查询时再 JOIN 实时分类表 | 分类被重命名/排序调整后，所有历史快照展示随之变化，违背快照"冻结当时状态"的初衷 |
| #4 | Minor | `getSnapshotById` / `getSnapshotList` 中执行 `categoryMapper.selectList(null)` 全量加载分类表 | 单条查询浪费明显；分类量增长后全表扫描不可接受 |
| #5 | Minor | `ProductSnapshotQueryDTO` 无任何 JSR380 校验，Controller 也未加 `@Valid` | `pageNum=0`、`pageSize=Integer.MAX_VALUE` 等异常参数直击 DB，存在 OOM 风险；违反后端规范第 8 条 |
| #6 | Minor | `createSnapshot` 上的 `@Transactional` 多余：单条 INSERT 且唯一调用方 `updateProduct` 已自带事务 | 噪声注解，`REQUIRED` 传播下形同虚设 |
| #7 | Minor | 列表查询固定模式 `WHERE product_id=? ORDER BY created_at DESC` 与索引不匹配：仅有单列索引 `idx_product_id` / `idx_created_at` | 走"过滤 + filesort"路径，分页越深越慢 |

---

## 二、改进措施

### 2.1 触发场景补齐（对应 #1）

- **`createProduct`**：插入商品主表后立即调用 `snapshotService.createSnapshot(product)`，作为商品的 v1 初始快照。
- **`deleteProduct`**：删除商品主表前先调用 `snapshotService.createSnapshot(product)`，避免硬删除后丢失被删前的最终状态。
- **`updateProductStatus`**：状态变更属于业务关键事件，修改前先落快照。
- **`updateProduct`**：保留原有"修改前快照"行为。

四处变更点的事务由调用方 `@Transactional(rollbackFor = Exception.class)` 统一保证原子性。

### 2.2 错误码修正（对应 #2）

- 在 `ResultCode` 中新增 `SNAPSHOT_NOT_FOUND(3006, "商品快照不存在")`。
- 在 `BusinessExceptionEnum` 中同步新增 `SNAPSHOT_NOT_FOUND(ResultCode.SNAPSHOT_NOT_FOUND)`。
- `getSnapshotById` 改用 `BusinessExceptionEnum.SNAPSHOT_NOT_FOUND.getException()` 抛出。

### 2.3 分类信息冗余落库（对应 #3）

#### 数据库层（Flyway V3）
- 新增列：`category_name VARCHAR(100)`、`category_sort INT`，均 DEFAULT NULL，注释明确"冗余，快照时刻冻结"。
- 新增联合索引：`idx_product_id_created_at (product_id, created_at)`，覆盖固定查询模式。
- 数据回填：`UPDATE t_product_snapshot s INNER JOIN t_product_category c ON s.category_id = c.id` 将存量快照的分类信息按当前状态回填（历史快照无更精确的"当时值"，这是最佳近似）。

#### 实体与 VO 层
- `ProductSnapshot` 实体新增 `categoryName` / `categorySort` 字段。
- `ProductSnapshotVO` 原本就具备对应字段，无需改动。

#### 服务层
- `createSnapshot` 中通过 `categoryMapper.selectById(product.getCategoryId())` 一次性取分类详情并写入冗余字段。
- `getSnapshotById` / `getSnapshotList` 改为直接读取快照自身的 `categoryName` / `categorySort`，**彻底移除 `t_product_category` 的 JOIN**，从根本上解决 #4 的全表扫描问题（同时减少一次 SQL 与 Map 装配）。

### 2.4 移除冗余 `@Transactional`（对应 #6）

`createSnapshot` 去掉 `@Transactional(rollbackFor = Exception.class)` 注解：
- 内部仅一次 `insert`；
- 所有调用方（`createProduct` / `updateProduct` / `deleteProduct` / `updateProductStatus`）均自带事务，会话加入外层事务即可。

### 2.5 参数校验接入（对应 #5）

- `ProductSnapshotQueryDTO`：
  - `pageNum`：`@NotNull` + `@Min(1)`
  - `pageSize`：`@NotNull` + `@Min(1)` + `@Max(200)`（防止恶意大页码 OOM）
- `ProductSnapshotController.getSnapshotList` 形参加 `@Valid`，触发 `BindException`，由现有 `GlobalExceptionHandler` 统一捕获并返回 `Result.validateFailed(message)`。

## 四、改进前后对比

| 维度 | 改进前 | 改进后 |
|------|--------|--------|
| 快照触发 | 仅 `updateProduct` | `create / update / delete / status` 全部覆盖 |
| 错误码语义 | 缺快照时返回"商品不存在" | 返回"商品快照不存在" |
| 分类信息展示 | 跟随 `t_product_category` 实时变动 | 冻结在快照产生时刻 |
| 分类查询 | 每次列表/详情都 `selectList(null)` 全表 | 无 JOIN，零额外查询 |
| 参数校验 | 无 | JSR380 + `@Valid` + 全局异常捕获 |
| 注解噪音 | `createSnapshot` 多余 `@Transactional` | 移除 |
| 查询性能 | 过滤后 filesort | 命中 `idx_product_id_created_at` 联合索引 |

## 五、后续可考虑（未实施）

1. **清理 `ProductServiceImpl#getCategoryMap` 全表加载**：与 #4 同源，但属于商品服务范畴，未在本次快照审查中处理；可后续抽公共组件 `CategoryQueryHelper` 统一按 ID 集合批量取。
2. **快照表增加 `mutation_type` 字段**：标记本次快照来源（创建/更新/删除/状态变更），便于审计过滤；可下一次迭代加入。
3. **`deductStock` / `rollbackStock` 是否需要快照**：取决于库存变更是否需独立审计。若需要，可在此二处也接入 `createSnapshot`。
