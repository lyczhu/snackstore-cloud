## D1 · 补偿机制选型 —— 选 **方案 C（幂等流水 + 订单标记 + 定时对账）**

| 选项 | 思路 | 优点 | 代价 | 结论 |
|---|---|---|---|---|
| A 不补偿 | 超时也直接回滚，泄漏靠人工对账 | 零改动、语义不变 | 泄漏无自动兜底（即现状，风险 R5 原样保留） | ❌ 拒绝：未消除风险 |
| B outbox 意图先行 | 订单事务内落「扣减意图」，提交后异步扣减 | 语义最干净，重试有据 | 下单从同步成功变**异步受理**，接口与状态机语义改动面大（违反 K2/K6 精神） | ❌ 拒绝：改动半径远超问题本身 |
| **C 幂等流水 + 标记 + 定时对账** | S1 流水表 + S3 旁路字段 + S4 复用 `cancelOrder` | 改动最小、状态机不变、补偿复用现有原子流转 | 超时瞬间对用户返回成功，稍后可能自动取消（需产品确认） | ✅ **选中** |
| D Saga / Kafka 事件 | 扣成功发事件，订单侧消费确认 | 最终一致性最强 | 新增 topic + 消费链路；本项目只有「订单→库存」一步跨服务动作 | ❌ 拒绝：性价比不成立 |

**失效条件**：若产品明确不接受 C 的用户感知（D-Open-1），则退化为「S0+S1+S2+人工对账 SOP」，C 的 S3/S4 不再适用。

## D2 · 幂等化是**前置**而非并列项

- **结论**：S1（`stock_deduction_log` + 幂等扣减/回滚）必须先于任何补偿逻辑上线。
- **取舍理由**：补偿的固有动作是「重试」；在 `(order_no, product_id)` 无唯一约束的库存更新上重试，等价于随机增减库存（K5）。
- **附带收益**：幂等化独立修复「并发双回滚 → 库存翻倍」，即使补偿方案整体被否，S1 仍有正收益 → **不构成沉没成本**。
- **一个重要的二级收益（2026-10-19 用户确认单实例后补写）**：幂等化把 Redis 分布式锁从「正确性前提」降级为「资源优化」。因为补偿的并发重复执行在 `uk_(order_no, product_id)` 上只会得到既有结果，**不产生错误数据**——所以单实例部署下可以安全地不加锁，未来扩容也不会因此出事故。
- **被拒替代**：只在 order 侧做「查询后决定是否重试」而不改 product —— 拒绝，因为查询与扣减之间存在竞态窗口，且回滚侧仍非幂等。

## D3 · 用**旁路字段** `stock_confirm`，不新增订单状态值

- **结论**：`t_order.stock_confirm TINYINT DEFAULT 1`，状态机保持 `0/1/2`。
- **取舍理由**：新增「3=库存待确认」会同时触碰 K2（统计 SQL 的字面量口径）、取消/支付/删除三处条件更新的语义、网关与前端对状态的既有假设——而这些**全都没有测试保护**（风险 R1/R8）。旁路字段把这些扩散全部切断。
- **代价**：多一个需要理解的概念；「订单可见但可能被自动取消」这一中间态在状态字段上不可见，只能靠 `stock_confirm` + 日志/指标解释 → 由 S5 的 gauge 与文档补齐。
- **被拒替代**：用 `status=3` 表达确认中 —— 拒绝（扩散面不可控）；把确认状态只存 Redis —— 拒绝（补偿需要可与订单同生共死的持久锚点，Redis 非数据所有者）。

## D4 · 超时分支需要**配置开关**

- **结论**：S3 的异常分流以 `order.stock-confirm.enabled` 之类开关控制，默认关闭，灰度开启。
- **理由**：S3 是唯一改变对外可观察行为的切片（下单失败 → 下单成功），属于不可逆用户感知变更；开关把回退成本从「回滚发布」降为「改配置」。
- **代价**：一条需要长期维护的分支，需在方案稳定后清理（建议 1 个版本内移除开关）。

## D5 · 回归防线（S0）先于业务改动

- **结论**：在动任何库存/订单代码之前，先落 3 条特征化测试 + 最小 CI。
- **理由**：本次评审的 P0 是「30 项已修复但无一条测试」；S1–S4 恰好落在最不能改错的金额/库存/状态三者交汇处。没有 S0，DoD 中的第 5 条（看板数值不变）无法客观判定。
- **被拒替代**：靠人工回归清单 —— 拒绝，清单目前只存在于未被 git 跟踪的 `docs/`（R11），且已在两轮修复中与现实脱节。

## D6（关联议题，**独立决策**）· 库存写接口是否迁到 `/internal/**`

- **现状**：库存扣减/回滚挂在公开面 `POST /products/stock/batch-*`，与同服务已有的 `/internal/products` 契约面不一致（评审 R12、依赖分析 F）。
- **建议**：**与 S2 同期评估但独立发布**。把 S2 的新查询接口放到 `/internal/**` 是正确的；顺手把已有写接口迁移会同时触碰 order 侧 Feign path 与网关 6 条 admin-only 模式，属于「用发布风险换一致性」，应单独批准。
- **失效条件**：若 order 侧短期要改 `createOrder`（S3），则此迁移必须推迟，避免同一时期在同一条边上叠两个变更。
