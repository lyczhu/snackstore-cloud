# 库存补偿方案（H6 残余风险）

> 状态：**方案讨论稿，未实施**
> 关联：`docs/系统审查报告.md` H6（扣库存先于订单入库，且无补偿）

## 背景

`createOrder` 现已修正为先插订单（PENDING）+ 订单项、再调用 product-service 扣库存（`batchDeductStock`），订单号使用 `IdWorker.getIdStr()` 消除碰撞。残余风险仅剩：

- **Feign 超时窗口**：扣减请求已到达 product-service 并提交，但响应在网络中丢失（超时/连接断开），order-service 捕获异常回滚本地订单 → **库存已扣但订单不存在，永久泄漏**。
- 触发条件苛刻（需"服务端已扣 + 客户端超时"同时满足），概率低但无任何兜底。

## 前置缺口：product-service 扣减/回滚不幂等

- `ProductServiceImpl.batchDeductStock` / `batchRollbackStock` 仅对 `stock` 列做条件更新（`.setSql("stock = stock ± quantity")`）。
- **无扣减流水表、无 `order_no` 唯一约束**——同一 orderNo 重复扣减/回滚会重复生效。
- 补偿任务每次重试/回滚都必须幂等，否则补偿动作本身会制造新的库存漂移。**任何补偿方案必须先做幂等化。**

## 推荐方案（C）：扣减结果标记 + 定时核对补偿

### product-service（幂等化 + 查询接口）

1. V4 迁移建流水表 `stock_deduction_log`：
   - `order_no` 唯一约束，`product_id`、`quantity`、`status`（DEDUCTED / ROLLED_BACK）、`deduct_time`、`rollback_time`
2. `batchDeductStock` 事务内写流水；同一 orderNo 重复调用直接返回已有结果（不重复扣）
3. `batchRollbackStock` 同理：流水已 ROLLED_BACK 则 no-op（顺带堵住并发双回滚导致的库存翻倍）
4. 新增 `GET /internal/stock/deduction/status?orderNo=`：返回该订单扣减流水状态（未扣/已扣/已回滚）

### order-service（标记 + 定时补偿）

5. V2 迁移：`t_order` 加 `stock_confirm TINYINT NOT NULL DEFAULT 1`（1=已确认，0=结果未知待确认）
6. `createOrder` 区分异常：
   - 业务失败（`Result.data=false`，库存不足）→ 保持现状抛 `STOCK_NOT_ENOUGH`，本地回滚
   - **超时类异常**（SocketTimeout/ConnectTimeout 等）→ 订单**不回滚**，事务提交并置 `stock_confirm=0`，接口照常返回成功
   - 理由：订单是补偿的锚点，回滚即失去补偿对象
7. `@Scheduled` 定时任务（建议每 5 分钟；多实例需 Redis 分布式锁防重复）：
   - 扫描 `stock_confirm=0 AND status=PENDING AND create_time < NOW() - 5min`
   - 查 product 扣减流水：
     - 已扣 → 置 `stock_confirm=1`（闭环确认）
     - 未扣 → 幂等重试 `batchDeductStock`
     - 重试超过 3 次仍失败 → 走现有 `cancelOrder` 原子流转（PENDING→CANCELLED + 幂等回滚；M15 已保证回滚结果被检查）
8. 任务只处理标记订单，不触碰正常未支付 PENDING 订单（不引入"超时自动取消未支付订单"的业务变化）

## 备选方案对比

| 方案 | 思路 | 优点 | 缺点 |
|---|---|---|---|
| **B：outbox 扣减意图先行** | 订单事务内先落"扣减意图"表（同事务），提交后异步执行扣减 | 语义最干净、重试有据 | 下单变异步受理，接口/状态机语义改动大 |
| **D：Saga / Kafka 事件** | 扣成功后发事件，订单服务消费确认 | 最终一致性最强 | 新增 topic + 消费链路，本项目仅"订单-库存"一步跨服务动作，性价比低 |
| **C（推荐）** | 幂等流水 + 订单标记 + 定时补偿，复用现有取消链路 | 改动最小，订单状态机 0/1/2 不变（旁路字段） | 超时瞬间用户看到"下单成功"但稍后自动取消，需产品侧确认可接受 |

## 风险与注意事项

- 超时分支提交事务意味着极端情况下用户会看到成功订单后被自动取消——需前端/产品确认该感知可接受；备选：超时也直接回滚并返回错误（放弃补偿，库存靠未来人工对账，不推荐）
- 定时任务与 `cancelOrder` 并发安全：依赖原子 `UPDATE ... WHERE status=PENDING` 影响行数判断，0 行即退出，不会双取消
- 幂等流水表需覆盖 `batchDeductStock` 的多商品场景（一个 orderNo 多行流水）
- product 侧流水与扣减需在同一事务（本地事务即可，无需分布式事务）
- 实施顺序建议：先做 product 幂等流水（独立且有即时效用），再做订单标记与定时任务
