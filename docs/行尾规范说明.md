# 行尾（Line Ending）规范说明

| 项目 | 内容 |
|---|---|
| 生效日期 | 2026-10-19 |
| 决策 | 仓库（index）与工作区（working copy）**统一 LF** |
| 落地文件 | 仓库根 `.gitattributes`（新增） |
| 同批变更 | `.gitignore` 移除 `docs/` 忽略规则，文档资产纳入版本控制 |
| 不做的事 | 不批量重写任何既有文件内容 |

---

## 1. 问题（修复前实测）

修复前仓库内没有任何 Git 属性文件，行尾转换完全交给各台机器的 Git 配置：

| 检查项 | 修复前实测结果 |
|---|---|
| `Test-Path .gitattributes` | 不存在 |
| `git check-attr text eol -- <任一受管文件>` | `text: unspecified`、`eol: unspecified` |
| `git config --show-origin --get core.autocrlf` | `file:D:/Programs/Git/etc/gitconfig  true` |
| 仓库级 / 全局级 `core.autocrlf` | 均未设置（值来自 Git for Windows 的**系统级**配置，不是开发者主动选择，也不随仓库走） |
| `git ls-files --eol` 分布 | 240 个受管文件：index 全部 `i/lf`；工作区 231 个 `w/lf` + 9 个 `w/crlf` |

由此产生的后果：

1. **同一份提交在不同机器上形态不同**。Windows 机器检出得到 CRLF 工作副本，Linux / CI 节点（`core.autocrlf=false` 或 `input`）检出得到 LF，行尾由环境而非仓库决定。
2. **入库内容由机器决定**。新写的文件是否被规范化为 LF，取决于"哪台机器执行 `git add`"，跨平台协作时 index 内容可能出现 CRLF 污染。
3. **工作区是否干净不可靠**。行尾差异会伪装成"文件已修改"，`git status` 的干净/脏判定在机器之间不可比，自动化脚本与 Agent 无法据此可靠决策。

---

## 2. 决策与取舍

采用 **`* text=auto eol=lf` + 显式源文件类型 `text eol=lf`**。

理由：

- 六个服务全部运行在 Linux 容器（`docker-compose.yml` + 各模块 `Dockerfile`，统一 EXPOSE 8080），`*.sh`、`*.yml`、`Dockerfile` 必须是 LF，否则容器内解释器与 Nacos 配置加载都可能出问题。
- `.gitattributes` 的优先级高于 `core.autocrlf` 与 `core.eol`，规则随仓库一起被克隆/检出，任何本地或全局配置都无法覆盖 → 行尾成为仓库属性，不再是机器属性。
- 新成员与 CI 无需再被告知"请把 core.autocrlf 设成某个值"。

被否决的备选：

| 备选 | 否决原因 |
|---|---|
| `eol=crlf`（工作区 CRLF） | 与 Linux/容器目标环境不一致，且会把 Windows 行尾强加给跨平台协作者 |
| 仅 `* text=auto`（不写 `eol`） | 只锁定仓库侧为 LF，工作区行尾仍由每台机器的 `core.autocrlf` 决定，未解决"依赖机器配置"这一根因 |

## 3. `.gitattributes` 规则清单

| 模式 | 属性 | 说明 |
|---|---|---|
| `*` | `text=auto eol=lf` | 兜底：按内容（NUL 启发式）识别文本，文本两侧都用 LF；未识别出的二进制不会被改动 |
| `*.java` `*.yml` `*.yaml` `*.xml` `*.md` `*.json` `*.properties` `*.sql` `*.txt` `*.csv` `*.dot` `*.dsl` `Dockerfile` `.gitignore` `.gitattributes` | `text eol=lf` | 项目实际使用的源码/配置/文档类型显式声明，防止将来有人放宽兜底规则后失守 |
| `*.sh` | `text eol=lf` | 容器内执行，必须 LF |
| `*.bat` `*.cmd` | `text eol=crlf` | 刻意的例外：`cmd.exe` 需要 CRLF |
| `*.jar` `*.war` `*.class` `*.png` `*.jpg` `*.jpeg` `*.gif` `*.ico` `*.pdf` `*.zip` `*.gz` `*.tgz` | `binary` | 二进制保护网，禁止任何转换与 diff/merge |

## 4. 对既有文件的影响：零内容重写

加属性后实测（`git status --porcelain`）：受管文件**没有**任何一个被判定为"已修改"，index 中的 240 个 LF blob 与清理后的工作区内容一致，因此不存在批量重写。

残留 9 个工作区仍为 CRLF 的文件（内容按约定保持不变，会在编辑或重新检出时自然归一）：

```
api-gateway/src/main/java/com/lawyus/snackstore/gateway/config/SentinelGatewayConfig.java
common/src/main/java/com/lawyus/snackstore/common/response/Result.java
docker-compose.yml
nacos-config/README.md
nacos-config/api-gateway-routes.yml
order-service/pom.xml
order-service/src/main/java/com/lawyus/snackstore/order/feign/product/ProductClientFallbackFactory.java
product-service/docs/商品快照功能技术文档.md
product-service/pom.xml
```

已知表现：对上述 9 个文件执行 `git add` 时，Git 打印**提示性** advisory（不是错误）：

```
warning: in the working copy of 'docker-compose.yml', CRLF will be replaced by LF the next time Git touches it
```

`git diff` 对这些文件无任何输出，`git status` 也不会把它们列为修改。若希望立刻消除该提示，需显式做一次归一并重新检出：

```bash
git add --renormalize .
```

此命令应单独成一次只含行尾归一的提交；本次变更**刻意未执行**，因为其中两个文件（`order-service/pom.xml`、`product-service/pom.xml`）带有未提交的实际改动，批量重写会干扰这些改动。

## 5. Git LFS 结论：本仓库非必需，故未声明

| 检查项 | 实测结果 |
|---|---|
| 全局配置 `filter.lfs.clean/smudge/process`、`filter.lfs.required=true` | 存在（由 `git lfs install` 写入用户全局配置，属机器级钩子） |
| `git lfs ls-files` | 空输出，零个 LFS 跟踪对象 |
| `git ls-files` 中的二进制扩展名文件（jar/war/png/jpg/…/class） | 0 个 |

结论：**没有需要 LFS 承载的大文件，`.gitattributes` 中不声明任何 `filter=lfs` 规则**。在没有匹配跟踪模式的情况下声明 LFS 过滤器，只会给每次文件操作增加 smudge/clean 进程开销。

未来引入大二进制资产时的写法（需与 `git lfs track` 一致）：

```
*.pak filter=lfs diff=lfs merge=lfs -text
```

另需知晓的机器级前提：全局 `filter.lfs.required=true` 意味着 `git-lfs` 可执行文件必须在 `PATH` 中，否则所有 Git 操作会直接失败。这与本仓库配置无关，但换机器时需要检查。

## 7. 各环境注意事项

- **无需**再为本仓库调整 `core.autocrlf` / `core.eol`；`.gitattributes` 优先级更高，改了也不生效（这正是解耦的目的）。
- **IntelliJ IDEA**：`Settings → Editor → Code Style → Line End Separators` 选 `Unix and macOS (\n)`，避免编辑器主动写回 CRLF。
- **VS Code**：工作区设置 `"files.eol": "\n"`。
- **CI / Linux 节点**：无需任何行尾相关配置或预处理脚本。
- **新增二进制文件**：为其补充显式 `binary` 规则，不要只依赖 `text=auto` 的内容嗅探（空文件或纯 ASCII 二进制可能被误判为文本）。
- **不要用写文件工具生成 CRLF**：本次新写的 `.gitattributes` 与本文档首次落盘都是 CRLF，必须校验并归一为 LF。做法：按字节统计 `0x0D` 数量应为 0（同时确认无 UTF-8 BOM、文件以 `0x0A` 结尾），归一时用无 BOM 的 UTF-8 显式写回，不要用重新输入文字的方式修补。

## 8. 附带变更：`docs/` 纳入版本控制

本次同时删除了 `.gitignore` 中的：

```
# documents
docs/
```

影响：

- 根 `docs/`（架构分析、审查报告、DOT/Structurizr 模型、本说明）不再被忽略，`git check-ignore -v docs/` 返回未忽略。注意：这些文件目前仍是**未跟踪**状态（`git status` 显示 `?? docs/`），必须 `git add` 并提交后才真正进入版本控制。
- 补充事实：`docs/` 这条忽略规则只存在于本次工作区里那份**未提交的** `.gitignore` 改动中，`HEAD` 提交版本的 `.gitignore` 并无该规则；因此删除它相当于把这部分本地改动还原，不影响已跟踪文件。
- 该规则原本**不带前导斜杠**，因此也屏蔽了各级模块的 `docs/`。取消后 `api-gateway/docs/`、`user-service/docs/ADMIN_ACCOUNT.md` 等同样变为待跟踪；`product-service/docs/`、`product-search-service/docs/` 下部分文件此前已被跟踪，不受影响。
- 首次提交前请逐个确认这些新暴露的文档确实需要入库；若某类文档仍需忽略，应改用**带前导斜杠**的精确规则（例如只忽略 `/docs/scratch/`），不要再使用全局 `docs/`。
